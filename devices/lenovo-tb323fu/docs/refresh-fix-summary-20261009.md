# Y700 五代高帧率问题修复总结

设备：Lenovo Legion Y700 Gen 5 / TB323FU / SM8850。日期：2026-10-09。

本轮已将有效方案固化到平板：Gamescope 主包和 libs 均为 `1:3.16.31^1-1.100912.fc44.armada`，型号配置随启动自动生效，只保留30、60、90、120、164五档。用户已确认原生分辨率在最高性能档可达到164FPS。没有重启整机，停止继续收集FPS样本。

## 原来是什么问题

《土豆兄弟》切到90档能接近90FPS，切到120或164时反而降到约60或半刷新率；MangoHud曲线反复出现长、短帧。最初将它归因于限帧设置或CPU限制的排查方向不准确。

后台核对发现，Steam设置确实进入Gamescope的内部有效目标，120/164目标并没有错误变成60；实际面板也能输出164Hz。主要瓶颈在Gamescope的色彩合成与绘制时机：全屏透明HUD层仍逐像素做昂贵的色彩处理，合成成本约7.1—7.3ms；164Hz每帧只有约6.10ms，120Hz每帧约8.33ms，叠加等待和调度开销就容易错过显示时机，重复旧帧或延后新帧，产生掉到半速和曲线尖峰的表现。

同一游戏的短时色彩关闭对照，120档约60FPS可恢复到约119FPS；另一个对照仅隐藏HUD也能恢复高帧率。对照后恢复正常色彩和HUD。这些证据指向合成开销，不能把它解释成屏幕只能跑60Hz。

## 固化了哪些修复

1. **型号匹配与五档接入**：沿用Y700精确型号和内屏DSI匹配，只保留30／60／90／120／164，菜单里的设置通过Steam原生接口进入Gamescope。
2. **减少透明叠加层的无效工作**：对完全透明黑像素跳过不会影响其可见贡献的色彩矩阵和LUT计算；非透明内容保留原路径。
3. **优化原色彩算法**：四面体3D LUT仍使用原四次nearest采样，以无分支选择减少GPU分支成本；在符合条件的SDR未混合像素中省去重复的互逆transfer操作。完整色彩管理和正常HUD保留。
4. **改善新游戏帧的绘制机会**：已就绪、非FIFO游戏帧可使用本轮尚未消费的绘制机会；预算改为实际paint工作耗时，避免把此前等待时间算成绘制成本。机会受型号、内屏、固定刷新、身份和一次性消费条件约束。
5. **自动启用与维护包**：Y700 Lua启动时自动开启late-base与work-budget；无收益的cycle实验及诊断开关保持关闭。源码补丁、构建日志、包校验值随私有维护仓库保存。

透明与SDR快路径按精确`lenovo-tb323fu`型号启用。未启用三线性替代LUT、timerfd-read、HUD延后等没有通过或未验证的方案。未更改本轮CPU/GPU频率、温控或用户游戏存档。性能档由用户设置。

## 已验证结果

正常HUD、色彩开启、没有补帧的1920×1200《土豆兄弟》同一标题场景，各30秒记录取25秒稳定窗：

| 选择档位 | 自测游戏FPS | P95帧间隔 |
|---|---:|---:|
|30|29.96|33.49ms|
|60|59.88|16.81ms|
|90|89.96|11.26ms|
|120|119.68|8.47ms|
|164|163.44|6.30ms|

用户另行确认：**原生3040×1904分辨率、最高性能档也能达到164FPS**。此前约158.4的记录只代表当时性能状态和场景，不能作为原生分辨率固定上限。按用户要求，不再继续采样；退出游戏后的稀疏日志不作为游戏FPS证据。

上述五档自测对应固化前的同方案运行版本；最终RPM已通过远程构建、依赖预检、正常安装、文件完整性及运行二进制SHA核验。用户要求停止采样，因此没有将新包另做一轮FPS采样，也不把此前数据伪装成新包测试。
